pysepal-api

UI-free HTTP client for SEPAL platform services — status snapshot (2026-05-18)

What this is

A pure-Python HTTP client library for the SEPAL platform's user-files, tasks, and processing-recipes services. No Solara, no Voila, no Jupyter widgets — that lives in pysepal. This package is what you import from notebooks, CLI scripts, background jobs, or other Python code that needs to talk to SEPAL without dragging in UI dependencies.

Built on httpx with both sync and async clients, pydantic v2 models, and a drop-in compatibility shim for the legacy pysepal v3 SepalClient.

What we've built

Core client (sync + async)

  • SepalClient — sync, context-manager friendly, with auth/host/verify resolution from env (SEPAL_HOST, sandbox cookie, etc.)
  • AsyncSepalClient — full async parity, drives the same endpoint code paths
  • Transport layer with consistent error mapping (SepalAuthError, SepalAPIError, …)
  • Path helpers normalizing SEPAL's quirky /home/<user>/... conventions

Endpoints

EndpointOperations
user_fileslist, get, upload, download, createFolder (idempotent), module_dir helper
taskssubmit, list (with filters), get (with details), cancel, remove, restart, wait (terminal-state aware)
processing_recipeslist, get, save (gzip), delete

Compatibility

  • pysepal_api.compat exposes a SepalClient matching the legacy pysepal v3 surface so existing apps can swap imports without rewrites
  • cookies attribute is a dict (matches legacy behavior, not httpx default)

Quality gates

  • ruff + black lint, mypy --strict, pytest via nox
  • Tests use respx to mock httpx — no live SEPAL needed in CI
  • All gates green at v0.1.0

Goals

  • Be the lightweight, dependency-minimal HTTP layer that every SEPAL-aware Python project depends on.
  • Sync + async parity so notebooks, FastAPI services, and CLI scripts all get the same model.
  • Drop-in for legacy pysepal v3 SepalClient consumers — migration costs nothing.
  • Type-safe end to end (mypy --strict, pydantic v2 models).
  • Boringly reliable release pipeline: conventional commits → cz bump → GitHub Release → PyPI, no manual steps in the auth path.
